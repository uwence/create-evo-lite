## 实现细节 (Implementation)
[MemoryLockWinCimSnapshotReactivation]
[memory-lock-win-cim-snapshot-reliability] 由 parked residual 重新激活为 active release-gate reliability blocker；Task 5 收口挂起。

事实：Task 5(native 入口收口)产品实现经 PR #9 以真实 merge commit 合入 main@201ba1a(双亲 3eef744 + f4183e9)，PR CI 首跑 5/5(run 30693929859，含 windows node 22 与 24)，代码复审 ACCEPTED。但 main push release-gate run 30694812371 首跑 4/5，唯一失败为 windows-latest/node 24 的 T-lock-ident「self snapshot alive」(actual null)。经一次显式授权的 job 级重跑(仅 job 91355736720)后，attempt 2 在同一位置以同一方式再次失败。因此 Task 5 closure 保持 BLOCKED —— 未通过的是门，不是合入。

关键转折：重跑此前一直能掩盖这个 residual(run 30601168988 与 30690469066 均为首跑红、重跑绿)，这一次掩盖失败了。在同一 commit、同一 runner 镜像上连续两次失败，它不再符合「偶发、可重跑消除」的定性，因此不再按普通 flake 处理。

已确定的一层根因：两次失败的耗时分别为 10.123 秒与 10.020 秒(从 T-lock-ident 开始到断言失败)，精确落在 getProcessSnapshot 对 Windows 查询设置的 execFileSync timeout 10000 毫秒边界上。因此当前最强推断是命令达到超时，而不是「CIM 成功返回空对象」。getProcessSnapshot 把 PowerShell 启动失败、超时、非零退出、空输出、JSON 解析失败与空 CIM 行全部折叠为同一个 null，所以现有日志无法进一步区分。

尚未证明：耗时落在 powershell.exe 启动、profile/模块初始化、Get-CimInstance 本身、CIM provider 不响应，还是已产生部分输出但进程未退出。同一产品内容在 pull_request event 下 windows 22/24 首跑双绿、在 push event 下 node 24 两跑皆败，这一 event 差异目前只是待验证假设，不构成因果结论。

范围与禁令：Phase 1 只做观测与分类，不做生产修复。禁止盲目增加 timeout、函数内自动重试、把 null 视为 alive、把 T-lock-ident 降级为 warning、删除 Windows 真实集成测试、按 Node 版本跳过。目标是先把确定性身份判断合同与 Windows CIM 集成可用性探针拆开。

未推进：Task 6 marker/recovery、Task 7 verify、Task 8 release enforcement 均未授权且未实现；[zvec-win-unicode-containment] backlog 条目未 resolve；正式发布与 Windows 非 ASCII rollout 继续阻断。
