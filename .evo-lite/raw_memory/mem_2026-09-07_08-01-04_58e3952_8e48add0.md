缺陷性质是合同被绕过，不是逻辑写错。resolveLinkedPlanIds 在自己的头注释里声明过合同：「两种官方机制可能对『某 spec 是否有关联 plan』给出不同答案，任何需要这个答案的地方必须调用本函数，而不是自己再推导一遍」。同一棵树里有两个消费者自己重推了：scan.js 只按声明的那一半写 IR，于是 traceability、plan status 和 inspector 读回的是窄答案，而 Spec Portfolio —— 唯一真正调用该函数的 caller —— 看到的是宽答案。plan.linkedSpec 是受支持且正确的声明方式，只是没能活着写进 IR。

来源与账单：hungersnakegame8 报了两次。第一次被标记为已收集，实际只发了 lint 那一半；子巢于是带完整复现重报（chains=7 unlinked=5 → 加一个冗余 frontmatter 字段后变 12/0）。代价落在作者身上：spec 必须在自己的 frontmatter 里重复一条它的 plan 已经声明过的链接。要求每对新 spec/plan 都带上的 workaround 不是约定。

母仓同样中招，不是子巢特有：45 个 spec 中 3 个 linkedPlans 为空而 plan 反向指回；chains 244 → 267，unlinked tasks 49 → 26，drift 不变（R008 72、R005 4、R010 3、R011 2、R009 1）。

不变量保持：resolution 跑在交叉校验循环之后，那些循环逐位不变。「这个 spec 点名的 plan 存在吗」这条警告必须继续裁判作者写下的东西，反向链接不得让它免检 —— 因为声明本来就来自 plan 那一侧。

可证伪性：T-scan-reverse-link 用两条负控钉住性质 —— 指向别的 spec 的 plan 不得挂上；正向引用一个不存在的 plan 仍须告警。突变负控：移除 resolution 后，套件恰好红在被守护的那条断言（「仅凭反向声明也必须产生链接」），别处不红。
