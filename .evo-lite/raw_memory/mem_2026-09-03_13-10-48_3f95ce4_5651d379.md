owner 决定(2026-09-03,两条):新建子巢默认安装并启用 zvec,装失败才回落 sqlite;将 zvec
pin 到 v0.7.0。该决定 supersede 了 spec:zvec-memory-index 的 Non-Goal「Forcing Zvec on
hive children」,已在 spec 内划线并原地记录修订(issuer / date / 改了什么没改什么)。

改动:templates/runtime/package.json 增加 optionalDependencies @zvec/zvec 0.7.0;
产品根 pin 0.6.0 → 0.7.0;两份 lockfile 与母仓自身 runtime 镜像同步重生成;
T18e 新增断言把产品 pin 与子巢清单 pin 锁在一起,并要求 lockfile 真的携带该条目且
optional:true(npm ci 会拒绝 lockfile 未覆盖的清单,那会让每个新子巢 runtime-not-ready)。

「启用」不需要改代码:DEFAULT_ENGINE_CHOICE 早已是 zvec,子巢那句警告恰恰是引擎选了
zvec 而找不到包。缺的从来只有「装」。

关键认识:母仓能用 zvec 是拓扑巧合 —— 它向上解析到产品自己的根 node_modules,因为母仓
就是产品本身;子巢头上没有那个父级。因此母仓上观察到的 zvec 表现从来不能当作子巢证据。

顺带修掉一处在本次改动之前就已为假的陈述:scaffold 无条件打印「运行时引擎已锁定为
sqlite-fts5-trigram」,而没有任何代码在 scaffold 时写 memory-engine.json,默认也早已 flip
到 zvec。改为按磁盘实际报告,且只 resolve 不 require —— 非 ASCII 路径上加载原生模块可能
终止进程,那正是包容守卫存在的理由。

验证:新建 hungersnakegame8(已注册进母巢,hive status = up-to-date)。清单/lockfile/磁盘/
解析路径(realpathSync.native 复核)/引擎(model=zvec-jieba-fts, match_source=zvec-fts)/
写读闭环 全部成立;突变负控:移开 @zvec → 出现原报告的回落警告且 model 转 sqlite,恢复后
回到 zvec —— 同时验掉「引擎真是 zvec」「回落路径活着」「原警告即缺包路径」三件事。
CI release-gate 6/6:win32 node22/24 · ubuntu node20/22/24 · containment 合同证据。

边界(未做):zvec 仍是 optional 不是硬依赖;nurture 仍不向存量子巢推原生依赖;非 ASCII
