Spec 状态词汇表收敛（分层清洗第 1 层）+ 一处 park 误判更正。PR #43 合入 main@e7488aa，PR #44 合入 main@0965f6e，两个 PR CI 均 6/6 全绿。

背景：用户提出对 evo-lite 历史包袱做局部大清洗（删除格式不合规、与近期实施无关的 plan/spec）。实测数据否定了该筛选前提：母巢 47 个 plan 中 25 个（53%）无 id/status frontmatter，但其中大量是 100% 勾选完成的（verification-contract-phase0-3、2026-08-08 pr-state-sync 37/37、2026-08-09 postmerge-correction 25/25），说明 plan frontmatter 从未被强制过，不是历史遗留；CodePLC 则相反，用自由文本 status 表达进度而从不勾 checkbox（codeplc-foundation-implementation-plan 0/50 而 status=closed-completed-with-deferred-gates）。两个仓库使用两套不兼容约定，故"格式合规"与"完成度"均不承载真实语义，按其筛选必然误删。另判定：清洗与收口的核实成本完全相同（都需读 plan → 找产物 → 判断），只有终点不同（rm vs 标 done），故收口严格优于删除；且大规模删除本身是一次巨型治理提交，是 warning-driven governance 的极端形式。据此确定分层方案：第 1 层统一状态词汇表（不删文件）→ 第 2 层 disposition ledger → 第 3 层真删除，顺序不可逆。本次仅执行第 1 层。

第 1 层实施（PR #43）：buildSpecRegistry 此前只显式识别 done 与 parked，其余状态一律落入 adopted/active 兜底分支，而 portfolio 计数把该猜测呈现为事实。新增 RECOGNIZED_SPEC_STATUSES = {done, parked, adopted, active, draft}，状态在表外时产生 unknown-status 警告，并在条目上记录 declaredStatus 与 statusRecognized。实测：母巢 43 个 spec 零个越界（输出与改前逐字相同），CodePLC 12 个中 10 个越界，其中三个 closed-* 状态被兜底成 active/adopted——已完结议题被系统当作在飞，随后触发老化警告并反复吸引 agent 处理，是子巢 governance-work-budget 反馈所述循环的一条具体供料线。

关键设计约束：改动为纯增量，state 归类逻辑一行未动。理由是 deriveBlocker() 读取 state，重新归类会静默移动 release 门（impact 分析对 buildSpecRegistry 报 CRITICAL，9 个受影响符号、6 个直接调用者）。两条负控锁定该边界：未识别状态仍回落 adopted/active；带未识别状态的 release-blocking spec 仍产出 blocker。突变验证：注入 state='unrecognized' 后红点精确落在第一条负控断言上（非无关失败），恢复后 sha256 与基线一致（681737cff912d039）、双镜像字节相同、突变字符串确认清除。

实施中发现的陷阱：上游解析把缺失的 status 物化为字面量字符串 'unknown'，到 registry 层已无法区分"未声明"与"作者写了 unknown 这个词"。两者均按缺失处理并写入注释与测试（declaredStatus 对缺失返回 null，绝不返回上游字面量），否则每个无 frontmatter 的 spec 都会变成噪声而淹没真正的自创词。
