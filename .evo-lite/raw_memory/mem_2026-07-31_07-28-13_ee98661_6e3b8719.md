## 实现细节 (Implementation)
[Zvec06CorrectnessClosure]
[zvec-06-upgrade] 收口。议题由「功能升级」重分类为「P0 现存正确性缺陷修复」——原立项理由(0.5.0 无 readOnly、reader/writer 拆分随升级落地)被同版重测证伪：0.5.0 与 0.6.0 在七项跨进程 readOnly 矩阵上逐行相同，该矩阵保留为跨版本行为合同而非升级判据。

两处 P0 缺陷经真实 ZvecMemoryIndex.searchText() 路径复现并修复：
ZVEC-NS-ZERO-CANDIDATE-LEAK —— 0.5.0 无法区分「无 candidate 限制」与「过滤器命中 0 条」，空 namespace 的 scalar filter 回退成「不过滤」，recall(scope='code') 会返回 prose/symbol 档案，是确定性的 namespace 隔离破坏；
ZVEC-REOPEN-WRITING-SEGMENT-INVISIBLE —— 未 optimize 即关闭的写入在重开后仅 3/6 可检索；该状态正常可达(_finalizeSync 吞掉 optimizeSync 异常、进程被杀根本走不到 finalize)，档案静默不可召回且无任何报错。
两条已固化为常驻合同测试(T-zvec-namespace-isolation / T-zvec-reopen-visibility)，均验证过在 0.5.0 上失败于目标断言而非控制项。

不属于验收主张：delete+optimize 的 doc-id 空洞未在 Evo-Lite 复现(21 字段两版逐一相同)，已移除；只读 LOCK 文件权限修复属实但仅列为次要部署收益。

测量方法更正：readOnly 矩阵首次采集时 holder 子进程从游离的用户级 node_modules 解析到 0.5.0，构成 0.5-holder x 0.6-prober 混版测量；holder 钉到 require.resolve 绝对路径后对两版各重测，七行取值不变，结论依据由无效测量换为同版对同版。同一解析缺陷也是 release-gate Windows 侧连红八天的根因之一。
