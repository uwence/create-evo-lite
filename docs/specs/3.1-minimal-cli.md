# Minimal CLI

## Goal

交付 3.x 的第一个可安装形态。`npx create-evo-lite@next init` 之后，任何项目都拥有三个核心对象，并能用 `status` 看到机械事实、用 `render` 得到一张可读的进度页。

可验收判据：fresh clone → `npm install` → `init` → `status` → `render` → `test` 全绿，全程零原生编译。

## Non-goals

- 不做 CI / GitHub Actions。那是交付基础设施，够格单独一份 spec。
- 不做 search adapter、MCP、git hook、dashboard engine。禁区不变。
- 不做 HTML 主题系统。首版只有一个内联模板。
- 不提供 `--force`。3.1 不拥有覆盖用户文件的能力——那是不可逆操作。
- `init` 不修改任何已存在文件；所有命令都不创建也不修改 `.gitignore`。
- `render` 只允许创建或替换它唯一的生成物 `docs/project.html`，不得修改任何 canonical source。
- 不为 `PROJECT.md` 建 AST / IR，不推断 focus、lifecycle、blocked / doing / done。
- 不向用户项目下发 renderer 脚本。

## Design

### 1. 四个命令

```text
init     写五个文件：PROJECT.md / docs/devlog.md / docs/specs/TEMPLATE.md / AGENTS.md / CLAUDE.md
status   只报机械事实，见 §2
spec     复制 TEMPLATE.md 到 docs/specs/<slug>.md
render   CLI 内置，读 PROJECT.md + specs 文件信息 + 最近 devlog，单向生成 docs/project.html
```

`init` 只创建不存在的文件；任何已存在文件保持 byte-for-byte 不变；部分安装时补缺，并逐项打印 `created` / `skipped`——静默跳过会让人以为装全了。结束时提示用户把 `docs/project.html` 加进 `.gitignore`，但不代劳。

`spec <slug>` 不加日期前缀：日期会让同一个议题长出多份文件，而 slug 天然是 single owner。目标已存在时拒绝并退出非零，不覆盖。

`render` 是 projection capability：它缺席只损失 HTML，不损失接手能力，因为 Markdown 本身就可被人和 AI 直接阅读。

### 2. status：数据源钉死

```text
Initialized  PROJECT.md 是否存在
Project      package.json 的 name，缺失时退回目录名
Branch       git
Dirty        git
Specs        docs/specs/*.md 的文件数
Last log     docs/devlog.md 的第一个二级标题
Caps         见 §4；无 PROJECT.md 时 N/A
```

`Initialized  no` 是一个机械事实，不是特殊分支：此时其余字段照常输出并 exit 0——未初始化是一种状态，不是异常。

明确禁止：推断 focus 或 state、判断 blocked / doing / done、解析 Milestones 语义、从 checkbox 推导 lifecycle、建立 `PROJECT.md` 的 AST 或 IR。不报「哪个 spec 最新」——mtime 在 fresh clone 后失去意义，而按内容判定 active 就是 lifecycle。

### 3. structure 与 semantics 的分界

`status` **可以**读取 `PROJECT.md` 的结构与源文本——它必须读到字节才能数行——但**不得解释任何段落正文的自然语言语义**。

可以与 render 共享：section scanner、line counter、heading finder。不可以存在：「这句话意味着 blocked」「这段话是当前 focus」「这个 checkbox 表示 lifecycle=done」。

要保护的是信息流，不是文件布局。render 的 parser 输出只能流向 presentation，不得成为 status、lifecycle、focus 或 state 判定的输入。这条不靠约束模块结构来保证，靠 AC 里的 prose 负控证明。

### 4. caps：两个维度

**维度一，行数。** 八个段标题统一写成 `## Name (<= N)`，不带 lines / rows / items 字样。计数规则只有一条：

> 统计 section 内的非空源文本行。不计 section heading、代码围栏行本身、Markdown 表格的表头与分隔行。其余每个非空源文本行计 1。

**维度二，单行长度。** 每个非表格、非代码的正文物理行 <= 240 字符。

只有维度一会漏掉真正的病灶：2.x 的 FOCUS 是 1835 字符的一整段，在行数维度上是 `1/5`，读作 OK。一个报得出「看起来没问题」却没观察到真正问题的检测，正是 3.x 要避免的形状。

两个维度都只展示，不阻断：

```text
Caps    OVER — Decisions 21/20；Now 第 2 行 312 chars
exit    0
```

### 5. 预算

production JS 合计 <= 800 行，`test.js` <= 200 行。**这是设计预算，不是验收门。** 超出时要问的是「为什么多了 17 行，scope 膨胀了吗」，而不是机械宣布产品不合格；因此不许压缩代码保行数，而应重审 scope。

spec 的 120 行是另一回事：那是已经选定的 artifact 硬约束，所以它是 AC。

模板是纯文本 **seed，不是 mirror**：`init` 之后用户的文件允许永久分叉，不存在任何同步合同。这正是它与 2.x `templates/cli` ↔ `.evo-lite/cli` 那种逐字节镜像的根本区别，因此不计入预算。

### 6. Windows

```text
ASSUMPTION  尚未在真实 Windows 上执行。
ACTION      只用 path.join / Node fs / execFile；禁止 shell、symlink 假设、路径大小写假设。
STATUS      Not blocked.
```

Assumed 管「能不能继续工作」，AC 管「有没有证据宣布完成」。两者不合并，也不互相代替。

## Acceptance Criteria

- [x] fresh clone 后 `npm install` 成功，且未触发任何原生编译
- [x] `npm test` 调用仓库唯一的 `test.js`，覆盖 3.1 行为测试并以 exit code 0 通过
- [x] `init` 在空目录生成 §1 所列的五个文件
- [x] `init` 对已存在文件保持 byte-for-byte 不变，并逐项打印 created / skipped
- [x] `init` 不创建也不修改 `.gitignore`
- [x] `spec <slug>` 在目标已存在时拒绝并退出非零，不覆盖
- [x] `status` 的字段与 §2 钉死的数据源一一对应，不多不少
- [x] **prose 负控**：同一目录下，两份 heading、行数与表格结构完全相同、正文文字完全不同的 `PROJECT.md`，`status` 的输出逐字节相同
- [x] `status` 在无 `PROJECT.md`、无 git、无索引、无 hook、无 MCP 的目录中成功并 exit 0
- [x] caps 行数维度按 §4 的单一规则计数，八个段的实测值与人工核算一致
- [x] caps 长行维度能报出一个 1835 字符的单行段落；只报行数的实现会漏掉它
- [x] caps 任一维度超限时 `status` 打印 `OVER` 并以 exit code 0 退出
- [x] `render` 内置于 CLI；运行后用户项目中不存在 renderer 脚本
- [x] `render` 生成 `docs/project.html`，且全部源文件在前后哈希一致
- [ ] Windows smoke test：install / init / status / render 全部成功
- [x] 本 spec 自身 <= 120 行

## Open Questions

- 长行阈值 240 是初值，需在真实文档上跑一轮后复核；调整它不改变 §4 的结构。
- Windows smoke test 由谁在什么机器上执行尚未安排。它是关闭对应 AC 的唯一证据来源，Assumption 不能代替它。
